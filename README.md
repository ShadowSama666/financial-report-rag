# 申万食品饮料行业半年报问答知识库（方向 A）

面向 10 家食品饮料代表公司半年度报告的**可溯源 RAG 问答系统**，含双通道混合检索
（本地 Qwen3-Embedding 向量 + jieba/BM25 倒排）与课上演示级可视化前端。

## 二、快速开始

```bash
# 1) 环境
python -m venv .venv && .venv\Scripts\activate          # Windows
pip install -r requirements.txt

# torch 必须单独装，而且**不要用默认源**：PyPI 上 Windows 的 torch 轮子历来是
# CPU-only，直接 `pip install torch` 装出来的就是 +cpu 版，有显卡也使不上。
# 有 NVIDIA 显卡（CUDA 12.8+ / Blackwell sm_120 需要 cu128 及以上）：
pip install torch --index-url https://download.pytorch.org/whl/cu130
# 没有显卡再用这个（慢，见「阶段四·编码设备」一节的实测）：
pip install torch --index-url https://download.pytorch.org/whl/cpu

# 2) 密钥
copy .env.example .env        # 填入 DEEPSEEK_API_KEY

# 3) 阶段二：下载 10 家半年报
python download.py                      # 自动取最新一期
python download.py --year 2025          # 锁定 2025H1
python download.py --dry-run            # 只查询不下载

# 4) 阶段三：解析 + 切块 + 打标签
python build_kb.py                      # 约 2.5 页/秒，10 家约 30-60 分钟
python build_kb.py --company 600519 --limit-pages 40   # 冒烟测试
python build_kb.py --engine pypdf                       # 快速模式（牺牲表格结构）

# 5) 阶段四：建双通道索引（首次会下载 Qwen3-Embedding-0.6B ≈1.2GB）
python build_index.py --device cuda     # 有显卡：2717 块约 2.5 分钟（batch 16）
python build_index.py                   # 纯 CPU：实测约 15 小时，先看阶段四那节再决定
python build_index.py --limit 200       # 冒烟测试
python build_index.py --no-vector       # 只重建 BM25（秒级）

# 5b) 网络慢 / 权重下到一半卡住时，用这个抓模型（断点续传，可反复重跑）
python fetch_model.py --seed-from-hf-cache
#   完成后按提示把 .env 的 EMBED_MODEL 指向本地目录，之后全程离线：
#   EMBED_MODEL=C:/Users/.../sw_food_rag/models/Qwen3-Embedding-0.6B

# 6) 阶段五：可视化问答前端
streamlit run app.py                    # 浏览器打开 http://localhost:8501

# 7) 阶段六：评测 10 道题
python evaluate.py                      # 检索 + 生成 + 自动判官
python evaluate.py --no-generate        # 只测召回（不烧 token）
python evaluate.py --only Q09 Q10       # 只跑 2 道跨公司对比题
python evaluate.py --write-template     # 只刷新空白评分模板
```

> `data/pages/*.json` 是逐页解析缓存，`index/embed_cache.npz` 是编码缓存。
> 第一次跑完后，改切块 / 检索参数重跑只需秒级到分钟级（除非加 `--rebuild`）。

## 三、各阶段设计要点

### 阶段二　数据下载（`download.py` + `utils/cninfo.py`）

* 数据源：巨潮资讯网（cninfo.com.cn），是证监会指定的上市公司信息披露平台，
  比直接爬交易所站点稳定，且**沪深两市统一接口**。
* 三级 orgId 兜底：本地股票表 `szse_stock.json` → 关键词搜索接口 → 按市场前缀猜测。
* 用接口的 `category=category_bndbg_szsh` 精确锁定「半年报」，再用标题黑名单
  （摘要/英文/更正/取消…）二次过滤，避免把摘要当全文下载。
* 文件名规范 `{代码}_{简称}_{年份}年半年度报告.pdf`，阶段三靠它反解公司身份，
  因此**下游不依赖任何额外的映射表即可溯源**。
* 工程细节：请求间隔节流、指数退避重试、`%PDF` 魔数校验、小于 100KB 视为无效、
  先写 `.part` 再原子替换——中途断网不会留下半个损坏文件。

### 阶段三　文本提取与带标签切块（`build_kb.py` + `utils/`）

**① 表格结构还原**：pdfplumber 的 `extract_tables()` 拿到二维单元格矩阵，按
`行 = 单元格 | 单元格` 渲染成文本，并以 `【表格】` 标记。这是财务三表能被检索到的前提
（纯文本抽取会把整张表压成一行挤在一起的数字）。已与正文做行级去重，同一份数据不会进库两次。

**② 页眉页脚剔除**：半年报每页都重复「XX股份有限公司 2025 年半年度报告」与页码。
若不剔除，每个块都含公司名，BM25 的 IDF 会被整体拉平、公司名检索失效。
实现用**跨页频次统计**，但只在每页首尾 3 行内统计候选，且显式放过
（a）章节标题行、（b）含 ` | ` 的表格行——否则「货币资金 | 期末 | 期初」这类
跨页重复的表格行会被误杀。

**③ 切块策略**：先拼成全局长文本，同时维护「字符区间 → 页码」映射表，
在全局偏移上做滑窗（800 字 / 重合 120 字），切点从目标位置向前回溯最多 35%
找一个句末标点（`。！？；`），退而求其次找换行，实在没有才硬切。
这样块可以自然跨页，页码再由映射表反查，得到精确的 `页码:起始-结束`。
目录页（点线特征）整块丢弃。

**④ 标签注入**：每块生成两份文本——

```
tagged_text: 【公司:贵州茅台 | 申万行业:食品饮料 | 章节:第八节 财务报告 | 页码:30-31 | 块序号:66】
             一、营业收入 | 4 | 49,679,827,345.61 | 45,657,305,847.21 ...
text:        一、营业收入 | 4 | 49,679,827,345.61 | 45,657,305,847.21 ...
```

`text` 用于展示与喂给 LLM；`tagged_text` 用于编码（BM25 + 向量）。
把「这是谁家的、哪一节、第几页」一并编码进表示，是提升召回的最便宜手段
（`config.USE_TAGGED_TEXT_FOR_EMBED`）。

**⑤ 输出结构**（`data/chunks/chunks.jsonl`，每行一个块）：

```json
{
  "chunk_id": "600519-2025H1-0066",
  "company": "贵州茅台", "code": "600519",
  "sw_industry": "食品饮料", "sw_l2": "白酒Ⅱ",
  "doc": "600519_贵州茅台_2025年半年度报告.pdf",
  "section": "第八节 财务报告",
  "page_start": 30, "page_end": 31,
  "chunk_index": 66, "char_len": 786,
  "text": "...", "tagged_text": "..."
}
```

该结构直接支撑阶段五的**角标溯源**：`company + section + page_start/page_end`
即回答里那个可点击的出处角标。

## 四、阶段四：双通道混合索引（`build_index.py` + `utils/retriever.py`）

**向量通道**

* 编码对象是 `tagged_text`（带标签前缀），不是纯正文。标签里写着公司名、章节名、页码，
  编码进去相当于给每个块加了几个"语义锚点"——问"贵州茅台的财务报告"时，
  标签里的"贵州茅台""财务报告"会直接参与相似度计算。
* **非对称编码**：文档端裸编码，查询端套 `Instruct: {指令}\nQuery: {问题}`。
  这是 Qwen3-Embedding 的官方用法；建库与检索必须用同一套约定，否则向量不同源。
* 输出 L2 归一化向量，于是**内积 = 余弦相似度**，检索退化成一次矩阵乘法
  （`2717 × 1024` 的 `@`，毫秒级）。
* **编码缓存** `embed_cache.npz`：key 是 `sha1(模型名 + 文本)`。改了切块参数重跑时，
  只有内容真的变了的块会被重新编码。配套 `corpus_fingerprint()` 把块 ID 和文本摘要
  一起哈希进 `index_manifest.json`，语料变了而索引没重建会被立刻发现（而不是静默错位）。

**BM25 通道**：`jieba` + 金融自定义词典（公司简称、报表科目、报告结构词、行业黑话
如"渠道库存/批价/吨价/动销"）分词，`rank_bm25.BM25Okapi`（k1=1.5, b=0.75）。
落盘的是**分词结果**而不是原文，重建索引时不必再分词。

**PCA 底图**：建库时对全部向量拟合 `PCA(50)`，把 `mean` / `components` / `proj` 一起存下来。
这不是为了降维可视化这么简单——存下 `mean/components` 是为了让**查询向量能投到同一张图上**。
如果每次画图都重新拟合 PCA，查询点会落在另一套坐标系里，图上"离得近"就失去意义。
这是阶段五散点图能被用来**解释**检索结果的前提。

**编码设备：0.6B 模型在 CPU 上跑不动，这一条最贵**

本项目实测：2717 个块（平均 617 token、最长 803 token）用纯 CPU 编码，
**19.5~21.4 秒/块，全库约 15 小时**——和"几分钟"的直觉差了两个数量级。
同一台机器换成 GPU（RTX 5060 Laptop，8GB）后 **17~20 块/秒，全库 2.4 分钟**，
约 **370 倍**。过程里值得记下的几点：

1. **`pip install torch` 在 Windows 上装的是 CPU 版**。PyPI 的 Windows 轮子历来不含 CUDA，
   要装 CUDA 版必须走官方索引（`--index-url https://download.pytorch.org/whl/cu130`）。
   装完先自检 `torch.cuda.is_available()` —— 本项目就是带着一块空转的显卡，用 CPU 编了一轮才发现。
2. **先量再猜**。CPU 慢的原因一度怀疑是权重损坏、padding 浪费、线程超订，
   逐项排查（`torch.profiler` 显示 73.6% 时间在 `aten::mm`；随机权重同架构耗时一致；
   实际 padding 只到 batch 内的最大值）后确认：**就是纯算力不够**，
   CPU 的 GEMM 实测 339~399 GFLOPS，而 0.6B 模型 2717 块的浮点量摆在那里。
3. **batch 不是越大越好**。实测 8/16/32/48/64/128：
   batch 8 反而最快（20.0 块/秒），batch 32 之后不再变快（GPU 已饱和，
   而 padding 会垫到 batch 内最长的那条，batch 越大浪费越多），
   batch ≥64 直接把显存打爆（MLP 中间激活 128×803×3072×4B ≈ 1.3GB/张量）。
   本库默认 `EMBED_BATCH=16`：速度接近峰值，峰值显存 2.9GB，留足余量。
4. **CUDA OOM 会污染整个进程**。OOM 之后 CUDA context 进入 sticky error，
   同一个进程里后续所有调用都会连带失败，于是"在循环里 try/except OOM 继续试下一个 batch"
   会得出完全错误的结果（第一次 OOM 之后全是假失败）。**每个 batch 用一个独立进程测**才对。
5. **长任务必须能断点续跑**。`embed_cache.npz` 按 `sha1(模型名+文本)` 内容寻址，
   配合 `--checkpoint-every`（默认 256 块）定期落盘：中途断电/关机后重跑，
   已编码的块直接命中缓存，只补剩下的。这项改动是在"跑了两小时才 1% 的"情况下补的。

**权重怎么拿到（`fetch_model.py`）**：这一步在本项目实测中踩过坑，值得单独说。
国内镜像站（`HF_ENDPOINT=https://hf-mirror.com`）有两个坑：

1. huggingface_hub 1.x 默认改走 **xet CDN** 传权重，而镜像站没有该端点，
   表现是"下到 67MB 就彻底不动"。`HF_HUB_DISABLE_XET=1` 退回经典 HTTP 即可；
2. 退回之后，它的默认**读超时只有 10 秒**，慢网段必然反复触发
   `The read operation timed out` / `SSL: UNEXPECTED_EOF_WHILE_READING`。
   它虽然会 `Trying to resume download...`，但超时没变、间隔很短，
   实测会**卡死在某个整数分块边界**（本项目卡在 480 MiB）反复失败不再前进。

`fetch_model.py` 自己管下载循环：读超时放到 300 秒、失败退避重试、
每次用 HTTP `Range` 从已落盘字节数续传，并且能**直接接管 huggingface_hub
留下的 480MB `.incomplete` 半成品**（`--seed-from-hf-cache`），不重复花流量。
大文件下载完还会校验 LFS 的 `sha256`。抓完把 `.env` 的 `EMBED_MODEL` 指向本地目录，
之后建库 / 起应用 / 评测全程离线。

## 五、阶段五：可视化问答前端（`app.py`）

四个页签：

| 页签 | 内容 |
|---|---|
| 💬 问答 | 流式回答 + 回答里的每个【n】角标映射到出处卡片（公司 · 章节 · 页码 · 原文） |
| 🗺️ 文本块星图 | 2717 块降维散点图，点击任意点回显原文/公司/章节/页码；另有小倍数分面视图 |
| 🎬 检索动态过程 | 6 帧动画：语料 → 问题落点 → 向量 Top-K → BM25 Top-K → 最近邻连线 → RRF 融合 Top-N |
| 📐 方法与口径 | 数据来源、双通道机制、配色依据、已知限制 |

**动画怎么做的**：语料 3 个 trace 是静态的，只有 5 个"高亮" trace 参与帧动画
（`go.Frame(data=[...], traces=[3,4,5,6,7])` 定向更新）。若每帧都重画全部点，
页面要传 6 份 2717 点，白屏风险很高。检索页签还会把**真实算式**摊开给人看：
jieba 词元、向量范数、PCA 投影公式、以及每个块的 `1/(k+rank_v) + 1/(k+rank_b)` 明细。

**为什么只融合排名、不融合分数**：余弦相似度有界（0~1），BM25 分数无上界且随语料变化，
两者尺度不可比，直接加权会隐性放大大分数量纲的那一路。RRF 用 `1/(k+rank)` 把两路
压到同一尺度，k=60。

**跨公司配额轮转（对比题的成败点）**：问题里同时点名多家公司时，RRF 分数会被
"命中词最多的那一家"吃掉。实测 Q09（茅台/五粮液/老窖/汾酒）用 BM25 取 Top-8，
**8 块全部落在泸州老窖**；再经 `TOP_K_FINAL=6` 收口，其余三家一块都进不来——
对比题在**检索阶段**就已经退化成单公司题，后面的生成再强也救不回来。

这里要修的是**两层，只修一层不够**：

1. **通道层**（`PER_COMPANY_CHANNEL_K`）：`TOP_K_VECTOR` / `TOP_K_BM25` 是在融合
   **之前**按全池截断的，而且公司之间不加区分。实测 Q09 里山西汾酒向量排到第 21 名、
   BM25 排到第 36 名，两路 top-20 一个都没进——**候选池里根本没有汾酒的块**，
   融合层再怎么轮转也变不出来（轮转只能重排已有候选，不能凭空造候选）。
   打开后改为"每家公司每个通道各取 Top-N，再并集后按分数**全局重排**"
   （重排这一步不能省：只做首尾相接的话，各家自己的第 1 名会一起占住
   "全局第 1 名"的位置，RRF 的 `1/(k+rank)` 就失去可比性，融合分会失真）。
2. **融合层**（`BALANCE_MULTI_COMPANY` + `PER_COMPANY_K`）：候选池够宽之后，
   最终选取改为先按公司分桶、桶内按 RRF 降序、再轮转取用（每家先取第 1 名，
   再取第 2 名…，每家最多 `PER_COMPANY_K` 块）。它**不改 RRF 打分**，只改入围
   顺序，所以界面上 `RRF 总分` 列仍是真实分数，但"送入序号"不再严格单调递减——
   UI 与评测汇总里都显式标注了这一点，避免被误读成算错。

两层是**独立开关**，可分别关掉做 A/B（`PER_COMPANY_CHANNEL_K=0` 只关通道层）。

**轮转要对着"被问到的公司"轮，不是对着"检索范围"轮。** 这一条最初写错了，
而且只在界面上暴露：`search_trace(companies=...)` 这个参数被当成两个东西用——
① 检索白名单（= 侧边栏的「公司范围」，默认 10 家全选），② "这道题在问哪几家"。
早先直接拿 ① 当 ②，于是界面上问「对比茅台、五粮液、老窖的毛利率」时，
程序以为是 10 家公司的对比题，把 6 个名额轮转分给了 10 家 ——
实测最终 Top-6 落在五粮液/洋河/青啤/古井/伊利/海天，**被问的茅台、老窖一块没进**，
模型只能如实回"检索结果中未出现贵州茅台任何数据"。这看着像检索坏了，
其实是配额发错了对象。现在先用公司名在问句里做一次匹配得到 `targets`
（匹配不到才退回整个检索范围），**白名单仍按原范围过滤**，只把"对着谁轮转"改掉：

| 问句 | 检索范围 | `targets` | 最终 Top-6 的公司分布 |
|---|---|---|---|
| 对比茅台、五粮液、老窖的毛利率 | 10 家 | 点名的 3 家 | 五粮液 2 / 老窖 2 / 茅台 2 |
| 茅台、五粮液、老窖、汾酒的合同负债 | 10 家 | 点名的 4 家 | 老窖 2 / 五粮液 2 / 茅台 1 / 汾酒 1 |
| 贵州茅台 2026H1 营业收入 | 10 家 | 点名的 1 家 | 茅台 4 / 海天 1 / 青啤 1（不轮转） |
| 白酒公司怎么应对渠道压力 | 10 家 | 未点名 → 退回 10 家 | 6 家各 1 块 |

全 10 题复跑，黄金页命中与覆盖率与修改前**完全一致**（7/10 题命中、平均召回 60.0%、
覆盖率 100.0%）—— 评测题都在问句里点了名，所以这条修改对它们是恒等变换，
修的纯粹是交互侧的口径。
在真实 2717 块索引上跑全部 10 道题的实测：

| 配置 | 目标公司覆盖率 | 黄金页命中 |
|---|---|---|
| 都不开 | 91.0% | 8/26 |
| 只开融合层 | 97.5% | 8/26 |
| 两层都开（默认） | **100.0%** | 8/26 |

即覆盖率 91% → 100%，而**黄金页召回一分未少**。代价体现在精度上：为保证每家都有
名额，某家公司靠后的弱块也会被拉进来（实测 Q10 里山西汾酒 p124 那块讲的是
"应收账款/合同资产"，并未提及"合同负债"）。`trace.pool_counts` 记录候选池的公司
分布、`trace.company_counts` 记录最终配额，两者对比即可区分
"池子里就没有"（检索层问题）与"池子里有但没选中"（融合层问题）。

**配色依据（不是审美选择）**：散点图属于 **all-pairs** 形态——平面上任意两点都可能相邻——
所以必须用 all-pairs 判据校验。跑 `validate_palette.js` 实测：默认色板 8 个分类槽位在
all-pairs 下只有**前 3 个**能过（浅色最差配对 CVD ΔE 9.2 / 常视觉 ΔE 24.0，深色 9.4 / 20.9），
第 4 槽与第 2 槽同时出现时不达标。于是身份维度**硬性只用 3 个分类色**
（白酒 / 啤酒 / 大众品），公司级身份交给**小倍数分面 + 交互 + 明细表**承载，
不生成第 4 个色相、也不循环色槽。另：浅色下 aqua 对表面色仅 2.74:1（<3:1），
按补偿规则每个图表都配了明细表视图。深色是一套**独立取档**的色阶，不是把浅色自动反转。

## 六、阶段六：评测框架（`evaluate.py`）

**10 道题，2 道跨公司对比**（Q09 四家白酒合同负债/渠道打款节奏；Q10 五家白酒
毛利率 + 归母净利润增速）。每题在 `eval/questions.json` 里带：

* `key_points`：判分要点（"必须分别列出四家公司的合同负债期末余额，缺一家即扣分"）；
* `gold`：**人工核对过的黄金页**——答案真正所在的公司+页码。它是从原文定位的事实，
  所以能当召回率的分母，而不是拿模型输出去当标准答案。

**指标分三级，交叉才能定位问题**：

| 层级 | 指标 | 回答什么问题 |
|---|---|---|
| 检索侧 | 黄金页命中率、目标公司覆盖率、章节命中 | 该找的原文找到了吗？跨公司题四家都召回了么？ |
| 生成侧 | 角标合规（有无 / 是否越界 / 目标公司是否都被引用）、判官逐要点判定 | 块进来了，模型有没有用对？ |
| 归因 | 交叉判定 | 见下 |

归因逻辑（`attribute_failure()`）：黄金页一页没命中 → **检索漏召**；目标公司没覆盖全 →
**跨公司聚合失败**；黄金页命中了但判官认为有编造 → **生成幻觉**；否则取判官的失败分类。
这样"答错了"能落成"没找到"还是"找到了没用对"两种完全不同的修法。

**输出**（`eval/runs/<时间戳>/`）：
`scoring.csv` 逐题（含**留空的人工结论 / 人工失败原因 / 人工备注**三列，课堂上手填，
机器不覆盖；列顺序与 `scoring_template.csv` 复用同一份 `SCORING_FIELDS`，不会漂移）、
`recall_detail.csv` 逐块（公司+页码+命中来源+分数，即"召回了哪些文本块"）、
`results.jsonl` 全量中间态、`summary.md` 汇总。没有 API Key 时只跑检索指标，
人工列照常留空；`--no-generate` 可在不烧 token 的前提下单独测召回。

跨公司题额外记录 `公司配额` 列（每家各占了几块），用来区分两种不同的病灶：
**覆盖率 < 100%** = 某家在候选池里一块都没被召回（召回问题）；
**覆盖率 100% 但黄金页命中率低** = 配额不够，每家分的 1~2 块没踩在黄金页上
（选取问题，调大 `--top-n` 或 `PER_COMPANY_K` 即可）。

## 七、已知限制

* pdfplumber 对**扫描件 PDF** 无效（无文本层），需接 OCR。本次 10 家均为电子排版件。
* 复杂合并单元格（rowspan/colspan）的还原会有错位，属 pdfplumber 固有限制；
  影响的是表格可读性，不影响块级召回与页码溯源。
* 章节识别依赖「第X节」标题格式，各公司节号编排不一致（如茅台的财务报告是「第八节」
  而非「第十节」），代码按通用正则处理，不硬编码节号。
* 跨公司配额轮转会**牺牲一点纯分数最优性**换取覆盖率：轮转后"送入序号"不严格按
  RRF 总分递减，可能把某个跨公司高分块挤到后面。本项目的评测题里对比题优先，
  故默认开启；若要纯分数序，把 `config.BALANCE_MULTI_COMPANY` 置为 `False`。
* 配额轮转只在**选取层**兜住覆盖率，不会凭空造出候选：若两路都没召回某家公司的块，
  该家仍会缺席，此时 `目标公司覆盖率` < 100% 是真实的召回缺失。
* **两道跨公司对比题（Q09/Q10）黄金页召回为 0，但原因不同，且都不是配额造成的**
  （三种配额配置下同样是 0/4 与 0/10，已用 A/B 排除）。逐页核对原文后：
  * **Q09 是真实的检索失败**。每家公司都同时有两个地方出现"合同负债"：合并资产负债表
    （本题黄金页，如茅台 p26、老窖 p37、汾酒 p23）与财务报告附注。附注里有一条
    **标题就叫"合同负债"**（如五粮液 p89-90「23、预收款项 / 24、合同负债」），
    词面匹配强度远高于资产负债表里"混在几十个科目中的一行"，于是两路都把附注顶了上来。
    附注那条讲的其实是"期末无账龄超过 1 年或逾期的重要预收款项"，**拿不到本题要的金额**。
    检索与黄金页的差距在这里是实打实的。
  * **Q10 更像黄金页口径偏窄**。召回的泸州老窖 p14 直接就是一张
    「营业收入 | 营业成本 | 毛利率」表（酒类毛利率 85.51%），**本可直接回答该题**，
    但黄金页指定的是合并利润表页。年报的「管理层讨论与分析」常给出算好的毛利率表，
    对这类问题比利润表更直接。这属于**标注粒度**问题：黄金页记的是"最权威的原始出处"，
    不等于"唯一能回答的出处"。
  * 另有一处影响精度但不影响黄金页：Q10 里出现了「封面与重要提示」块（老窖 p1-3、
    汾酒 p1-3）——封面页含公司名与报告期，词面上容易命中，属于低价值块。
    切块阶段已用点线规则丢弃目录块，但封面页尚未过滤，是后续可优化项。
